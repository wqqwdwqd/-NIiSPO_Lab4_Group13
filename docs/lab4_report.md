### 5.3. Создание ReplicaSet

Для работы с несколькими Pod создан файл `replicaset-demo.yaml`.

**Содержимое файла:**

```yaml
apiVersion: apps/v1
kind: ReplicaSet
metadata:
  name: lab4-replicaset
  labels:
    app: lab4-rs-demo
spec:
  replicas: 3
  selector:
    matchLabels:
      app: lab4-rs-demo
  template:
    metadata:
      labels:
        app: lab4-rs-demo
    spec:
      containers:
        - name: busybox
          image: busybox:1.36
          command: ["sh", "-c", "sleep 36000"]
```

Для создания ReplicaSet выполнена команда:

    kubectl apply -f replicaset-demo.yaml

Для проверки использованы команды:

    kubectl get rs
    kubectl get pods -l app=lab4-rs-demo

**Полученный результат:**

    NAME               DESIRED   CURRENT   READY
    lab4-replicaset    3         3         3

Все три Pod находились в состоянии `Running`.

## 6. Ответы на контрольные вопросы

### 1. Что такое Kubernetes и зачем он нужен в работе с контейнерами?

Kubernetes — это платформа для автоматического управления контейнерными приложениями. Она позволяет запускать контейнеры, масштабировать приложения, распределять нагрузку и восстанавливать работоспособность после сбоев.

### 2. В чём отличие запуска контейнеров вручную через Docker от управления ими в Kubernetes?

Docker позволяет создавать и запускать отдельные контейнеры. Kubernetes управляет множеством контейнеров и узлов, поддерживает нужное количество экземпляров приложения, выполняет обновления и восстанавливает Pod при сбоях.

Например, Docker может запустить один контейнер, а Kubernetes может постоянно поддерживать три работающие реплики.

### 3. Приведите примеры задач, где оркестрация экономит время.

Первый пример — веб-приложение с большим количеством пользователей. Kubernetes может увеличить количество Pod при необходимости.

Второй пример — отказ контейнера. Контроллер Kubernetes автоматически создаёт новый Pod без ручного вмешательства администратора.

### 4. Назовите основные компоненты кластера Kubernetes.

Кластер состоит из control plane и рабочих узлов.

- `kube-apiserver` — интерфейс управления кластером.
- `etcd` — хранилище данных состояния.
- `kube-scheduler` — назначение Pod на узлы.
- `kube-controller-manager` — работа контроллеров.
- `kubelet` — запуск и контроль контейнеров на узле.
- `kube-proxy` — сетевое взаимодействие сервисов.
- Container runtime — непосредственный запуск контейнеров.

### 5. Как создать Pod с помощью YAML-манифеста?

Нужно создать YAML-файл с описанием Pod и выполнить:

    kubectl apply -f pod.yaml

Основные поля:

- `apiVersion` — версия API.
- `kind` — тип ресурса, например Pod.
- `metadata` — имя и другие метаданные.
- `spec` — описание контейнеров и параметров запуска.

Для простого Pod необходимо указать контейнер и его образ.

### 6. Приведите YAML-файл для простого Pod и объясните ключевые поля.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: simple-pod
  labels:
    app: demo
spec:
  containers:
    - name: nginx
      image: nginx:1.28
      ports:
        - containerPort: 80
```

`kind: Pod` определяет тип объекта. `metadata.name` задаёт имя. `image` определяет образ контейнера. `containerPort` указывает порт приложения.

Если пропустить необходимое поле, например `apiVersion` или описание контейнера, сервер API отклонит некорректный манифест.

### 7. Что такое сервисы Kubernetes? Разница между ClusterIP и Headless.

Service предоставляет стабильную точку доступа к группе Pod.

`ClusterIP` создаёт виртуальный IP-адрес для доступа внутри кластера и распределения трафика между Pod.

Headless Service использует `clusterIP: None`. Вместо общего виртуального адреса DNS может возвращать адреса отдельных Pod. Это удобно, например, для распределённых баз данных.

### 8. Чем отличаются NodePort и LoadBalancer?

`NodePort` открывает порт на узлах Kubernetes. Пользователь обращается к IP узла и назначенному порту, после чего трафик направляется через Service к Pod.

`LoadBalancer` использует внешний балансировщик нагрузки, предоставляемый облачной платформой или отдельной инфраструктурой. Пользователь обращается к внешнему адресу балансировщика, затем трафик попадает в Service и соответствующий Pod.

### 9. Какие порты задействованы и какие ограничения есть у NodePort?

Обычно используются:

- `nodePort` — внешний порт узла, по умолчанию из диапазона 30000–32767.
- `port` — порт Kubernetes Service.
- `targetPort` — порт приложения в Pod.

Диапазон NodePort можно изменить настройками кластера. Для доступа извне нужны сетевой маршрут и разрешение в брандмауэре.

### 10. Когда достаточно NodePort, а когда необходим LoadBalancer?

NodePort подходит для небольшого тестового приложения в локальной сети, когда известен IP узла.

LoadBalancer лучше подходит для публичного приложения, когда нужен стабильный внешний адрес и распределение запросов через балансировщик нагрузки.

### 11. Что такое Ingress? Пример манифеста.

Ingress описывает правила HTTP/HTTPS-маршрутизации к сервисам по имени хоста и URL-пути.

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: web-ingress
spec:
  rules:
    - host: example.local
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: web-service
                port:
                  number: 80
```

Запрос к `example.local/` направляется в Service `web-service` на порт 80. Для реальной работы Ingress необходим Ingress Controller.

### 12. Сравните Deployment, StatefulSet и DaemonSet.

**Deployment** используется для обычных, преимущественно stateless-приложений. Pod взаимозаменяемы, не привязаны к конкретным узлам и обычно не запускаются строго по порядку. Пример — веб-сервер. При трёх репликах создаются три Pod.

**StatefulSet** используется для приложений с постоянными идентификаторами и хранилищами, например баз данных. По умолчанию Pod создаются упорядоченно. При трёх репликах появляются Pod с устойчивыми именами, например `db-0`, `db-1` и `db-2`.

**DaemonSet** запускает Pod на каждом подходящем узле или выбранной группе узлов. Пример — агент логирования. Количество Pod определяется количеством подходящих узлов, а не обычным параметром `replicas: 3`. Если подходят три узла, обычно будут созданы три Pod.

### 13. В чём разница между Job и CronJob?

Job выполняет конечную задачу, например однократное резервное копирование данных.

CronJob создаёт Job по расписанию, например каждую ночь.

Проверка:

    kubectl get jobs
    kubectl get cronjobs
    kubectl describe job job-name
    kubectl logs job/job-name

Успешно выполненный Job обычно имеет статус завершения `Complete`.

### 14. Для чего нужны ConfigMap и Secret? Как передать данные в Pod?

ConfigMap хранит обычные параметры конфигурации, например адрес сервера или режим работы приложения.

Secret предназначен для чувствительных данных, например паролей и токенов.

Два распространённых способа передачи данных:

1. Через переменные окружения контейнера (`env`, `envFrom`).
2. Через файлы, смонтированные в контейнер как том.

Переменные окружения удобны для отдельных значений. Файлы подходят для конфигурационных файлов и данных, которые приложение читает с диска.

### 15. Приведите YAML-фрагменты ConfigMap и Secret.

Пример ConfigMap:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  APP_MODE: "development"
```

Пример Secret:

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: app-secret
type: Opaque
stringData:
  password: "demo-only-password"
```

ConfigMap не предназначен для хранения паролей. Secret обеспечивает отдельный механизм управления конфиденциальными данными и контроля доступа.

При этом Base64 не является шифрованием, а Secret без дополнительных настроек защиты также не гарантирует шифрование при хранении. Реальные пароли нельзя публиковать в открытом GitHub-репозитории.

### 17. Что такое namespace и зачем он используется?

Namespace — логическая область внутри Kubernetes-кластера для разделения ресурсов.

Он полезен, когда необходимо:

- отделить окружения разработки, тестирования и эксплуатации;
- разделить ресурсы разных команд;
- применять разные права доступа и квоты.

Например, можно создать пространства имён `dev`, `stage` и `prod`.

### 18. Как создать namespace и работать только в нём?

Создание:

    kubectl create namespace lab4

    kubectl get pods -n lab4

    kubectl apply -f pod.yaml -n lab4

Также можно установить namespace по умолчанию для текущего контекста:

    kubectl config set-context --current --namespace=lab4

### 19. Для чего нужны livenessProbe, readinessProbe и startupProbe?

`livenessProbe` определяет, работает ли контейнер. При повторяющейся неудаче kubelet может перезапустить контейнер.

`readinessProbe` определяет, готов ли контейнер принимать запросы. Если проверка не проходит, Pod исключается из подходящих конечных точек Service.

`startupProbe` используется для приложений, которым требуется длительный запуск. До успешного завершения этой проверки liveness и readiness проверки не выполняются.

### 20. Что такое PV и PVC? Как выделяется хранилище?

PersistentVolume (PV) представляет доступное постоянное хранилище кластера.

PersistentVolumeClaim (PVC) — запрос приложения на определённый размер хранилища и режим доступа.

PVC может быть связан с заранее созданным PV либо вызвать динамическое создание тома через StorageClass.

В данной лабораторной работе был создан PVC объёмом 1Gi с использованием StorageClass `standard`. PVC и соответствующий PV получили состояние `Bound`.

### 21. Как Kubernetes реагирует на отказ Pod или узла?

Основные механизмы самовосстановления:

1. ReplicaSet или Deployment создаёт новый Pod для восстановления количества реплик.
2. Kubelet может перезапустить контейнер, если он завершился или не проходит livenessProbe.
3. Если узел становится недоступным, контроллеры могут создать заменяющие Pod на доступных подходящих узлах.

Восстановление может занимать время и зависит от наличия ресурсов, настроек и состояния хранилищ.

### 22. Как обновить приложение без простоя? Что такое rolling update?

Rolling update — постепенное обновление Pod, при котором старые экземпляры приложения заменяются новыми.

В Deployment используются параметры:

- `strategy.type: RollingUpdate`
- `maxUnavailable` — допустимое число недоступных Pod.
- `maxSurge` — допустимое количество дополнительных Pod во время обновления.

Для обновления без заметного простоя также важны достаточное количество реплик, корректные readinessProbe и совместимость версий приложения.

### 23. Как запустить обновление приложения и следить за прогрессом?

Сначала можно изменить образ контейнера в Deployment:

    kubectl set image deployment/web web=nginx:1.28

Проверка процесса:

    kubectl rollout status deployment/web

Дополнительные команды:

    kubectl rollout history deployment/web
    kubectl get pods
    kubectl describe deployment web

При необходимости можно выполнить откат:

    kubectl rollout undo deployment/web

Эти команды приведены как теоретический пример. Развёртывание Deployment не входит в обязательную практическую часть задания для группы 13.
